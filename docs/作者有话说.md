# 作者有话说

## 我们为什么做 Burin

做 GUI 框架的人，本质上都在回答同一个问题：

> **"界面应该怎么写？"**

过去四十年，每一代框架都给出了自己的答案，每个答案都推进了某个边界。我们尊敬所有这些探索。

Burin 不是因为"别人做得不好"才做的。是因为我们想试试另一个方向。

---

## 关于前辈们

**Flutter** 用声明式 diff + relayout boundary + repaint boundary 建设了目前最完整的跨平台 GUI 体系。Google 的工程团队用数百万行代码证明了保留模式 + 增量更新的可行性。没有 Flutter 在前面趟路，我们的很多设计决策会少一个参考坐标。

**Iced** 把 Elm 架构带进 Rust。`Model → update(Msg) → view()` 的闭环在正确场景下极其优雅，类型安全的消息分发是 Rust 能提供的最好保证之一。

**Slint** 通过 DSL 编译器生成代码，运行时使用 `Property<T>` 实现依赖追踪——`get()` 时自动注册依赖，`set()` 时递归标记脏节点并懒求值。编译期负责常量折叠、绑定循环检测等优化，但依赖图的建立和更新是运行时的。这套机制在底层和 Burin 的 Signal 十分相似。区别在于：Slint 需要 DSL + 编译器来生成这段代码，由此换来了对多语言宿主（Rust / C++ / JS / Python）的支持和编译器级别的静态分析能力。代价是 UI 必须用 `.slint` 文件编写，不能纯 Rust 组合。

**Egui** 证明了即时模式在原型和工具类应用中的极致效率——零生命周期管理，零状态同步，写起来像写脚本。

**SolidJS/Leptos** 在 web 领域证明了运行时细粒度响应式是可行的——没有虚拟 DOM diff，读时自动订阅，写时精确通知。这个发现深刻影响了我们。

这些都不是"竞争对手"。它们是不同方向的探路者。

---

## 我们选了一条不同的路

Burin 的核心假设很简单：

> **如果不用 Rust 去适配某个已有的 GUI 范式，而是让 GUI 范式从 Rust 中长出来，会长什么样？**

Iced 问的是"Elm 怎么在 Rust 里跑"。
Xilem 问的是"React/SwiftUI 怎么在 Rust 里跑"。
Slint 问的是"怎么让一套编译时 DSL 跑在多种语言上"。

Burin 问的是另一个问题：

> **Rust 的 ownership、组合、零成本抽象，本身就暗示了一种 GUI 架构。把那套架构做出来。**

这个假设催生了三个设计选择：

### 1. 用信号代替消息

Elm 架构的 `update(Msg)` 在 Elm 里是模块化的，但在 Rust 里，消息枚举必须集中定义——每个新 widget 都要往同一份枚举里加变体，每个状态变更都要经过中央 `update` 函数。这在小型应用里优雅，在大型应用里变成单点耦合。

我们用 `Signal<T>` 代替：
- `Signal::read()` 时自动订阅
- `Signal::set()` 时自动通知所有订阅者
- Element 销毁时，`Drop` 自动退订

没有中央消息枚举。没有中央 `update` 函数。状态分散在各个 `Signal` 里，UI 组合即逻辑组合。

### 2. 让响应式贯穿全链路

SolidJS 证明了运行时响应式在 web 可行。但它追踪到的终点是 DOM 操作——浏览器内部的布局、绘制、合成是完全的黑盒。

Burin 的响应式追踪不止在"状态 → UI"这一层。它贯穿整个渲染管线：

```
Signal::set()
  → register_dirty(O(1))
  → process_dirty_set(O(k) 祖先上行)
  → Taffy 增量布局（MEASURE / REPOSITION / 跳过）
  → SubtreeCache 检查
  → 仅绘制脏子树
  → GPU / CPU
```

因为我们拥有整个管线，所以响应式系统不只告诉框架"什么东西变了"，它还精确告诉布局引擎"哪些节点需要重排"、告诉缓存系统"哪些子树可以直接复用"、告诉绘制层"哪些区域不需要重录"。

这不是比谁更聪明。这是 **Rust 给了我们浏览器不会给 web 框架的控制权**。

### 3. 纯 Rust，无 DSL，无宏 DSL，无代码生成

Burin 的 UI 是纯 Rust 函数调用：

```rust
VStack::new()
    .gap(12.0)
    .push(Text::new("你好").font_size(24.0))
    .push(Button::new("点我").on_click(|| println!("clicked")))
```

不需要学习新的模板语言。不需要等待代码生成。IDE 的自动补全、跳转定义、重构——全部开箱即用。因为编辑器看到的只是普通的 Rust 代码。

这不是"我们讨厌 DSL"。DSL 在正确的场景下极有价值（Slint 在嵌入式领域证明了这一点）。但我们的赌注是：**当语言本身已经足够表达力时，DSL 引入的学习成本和工具链断裂不值得。**

## Auralis：Rust 里的响应式内核

Burin 的响应式能力来自 [Auralis](https://github.com/chh-itt/auralis)——一个独立的开源内核，三个 crate，零平台依赖。

`auralis-signal` 的核心只有约 1300 行代码。`Signal<T>` 的内部实现是 `Rc<RefCell<>>`——没有依赖图拓扑排序，没有 Clean/Check/Dirty 状态机，没有 arena 分配。读时压入 subscriber 列表，写时遍历通知。你可以喝一杯咖啡然后完全理解它的实现。

这不是在追求"代码少就是好"。而是我们在赌：**简单意味着可被理解，可以被理解意味着可以被信任，可以被信任意味着可以在生产环境中用它做决策。**

Auralis 是独立发布的——你可以用它做任何事，不限于 GUI。SSR、CLI 工具、游戏逻辑、嵌入式设备。Burin 只是 Auralis 的一个消费方。

## 我们不是谁的替代品

Burin 有自己的最佳场景，也有明确的不适合场景：

**适合：**
- 中大型桌面应用——60 个内置 widget、Material 3 主题、Taffy 标准布局
- 需要 GPU/CPU 双后端保障的场景——同一套 Painter API，GPU 不可用时自动回退
- 高测试覆盖率要求的项目——TestHarness 让无窗口测试成为可能
- 需要精确手势处理的应用——GestureArena 的 7 种 Recognizer

**不适合：**
- 快速原型 → 用 Egui，即时模式的简洁无法被保留模式超越
- 嵌入式 / MCU → Slint 的编译时优化 + `#![no_std]` 是正确答案
- 已有 Dart 团队的跨平台项目 → Flutter 的生态不可替代
- Web 优先 → Dioxus/Tauri 的 WebView 路线更务实

## 最后的诚实

我们能做到从 `Signal::set()` 到 GPU 命令提交的整条链路都精确知晓"什么变了、什么没变"，不是因为我们比别人强——是因为 **Rust 的类型系统和 ownership 模型本身给了我们这些保证**：

- 谁拥有订阅？生命周期怎么管？→ Rust：`Rc` + `Drop`，不需要手动追踪
- 状态何时可变？线程安全怎么保证？→ Rust：`Cell/RefCell` + `!Send + !Sync`，编译期保证
- 脏标记怎么传播？指针会悬垂吗？→ Rust：`ElementId` 索引 + arena 分配，借用检查器兜底

也许顺着 Rust 的纹理走，是对的。也许不是。我们还不确定。

至于这个方向对不对——交给时间和你来验证。

## 补记：写完之后的意外发现

这篇文章写完后，为了确保对 Flutter、Slint、Xilem 的描述没有歪曲，我们去翻了它们的源码。

结果发现了一件没预料到的事。

Flutter 的 `BuildOwner._dirtyElements` + `PipelineOwner._nodesNeedingLayout`，Slint 的 `Property<T>` 运行时依赖追踪，和我们 `Signal<T>` + `dirty_registry`——三者底层的脏标记模型，几乎是同一套思路：**O(1) 标记 + O(k) 处理 + 边界短路**。

区别不在于"谁更先进"。区别在于怎么到达那里：
- Flutter 靠 Google 的工程团队多年迭代，百万行代码沉淀
- Slint 靠 DSL 编译器在编译期生成使用 `Property<T>` 的代码
- Burin 只是用 Rust 的 `Signal<T>` + ownership + `Drop`，就达到了同等架构质量

这不是设计上的巧思。这是 Rust 的语言能力本身把这条路铺好了——我们只是第一个踩上去的。

如果这个观察经得起社区检验，那也许，我们真的碰巧踩到了一条属于 Rust 自己的路。

不是我们找到了捷径。是捷径一直在那里。
